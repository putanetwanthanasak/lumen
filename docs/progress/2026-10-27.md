### Bugs found
1. **Review F1: a payday retry after a lost commit could debit the main account with no ledger record.**
   - Reproduced by `test_LO_06_retry_near_the_safety_net_records_the_money_that_moved` and `test_LO_06_retry_after_the_month_total_changed_records_the_money_that_moved`, both failing before the fix:
     - main account 2,400.00, leftover 1,800.00, commit lost after the bank call: the retry saw 600.00, chose `safety_net` and stored it, so 1,800.00 moved with no record;
     - with a new November installment before the retry, the bank refused the key ("idempotency key reused for a different transfer").
   - Root cause: the retry decided again from the current bank balance and month total, both of which may already reflect the first attempt.
   - Fix (`06dd5d2`): `BankAccountProvider.applied_to_savings(user, key)` returns what a key already moved; the run records that amount as `leftover_saved`, and the audit detail has `recovered: true`.
   - Not fixed here: `savings.auto_save` (manual entry and webhook, already on `main`) has the same pattern (`app/savings/service.py:101-105`). See Carry-over.
2. **Review round 2 F1: a buffer move whose commit was lost could credit the main account twice.**
   - Reproduced by `test_BF_09_lost_commit_then_another_move_never_credits_main_twice`, which failed before the fix with 1,000.00 credited against 500.00 withdrawn. The steps: move "a" (500.00, the whole buffer) loses its commit after the bank credit; move "b" (500.00) then succeeds; the retry of "a" gets 422.
   - Root cause: the main account was credited before the commit, so a lost commit left money credited with no ledger debit. Later moves were checked against a ledger balance that still counted it.
   - Fix (`6760d2d`, PR B): the router commits the withdrawal, then calls the bank. A repeat (DUPLICATE) calls the bank again under the same key, so a call that failed after the commit is completed by the client's retry. Proved by B62 and B63; BF-09's lost-commit test changed to the new order (a lost commit now moves nothing).
   - Trade-off: if the bank call fails and the client never retries, the buffer shows the move but the main account has not received it until a retry. This is the R4 outbox case (Carry-over). It never creates money.
3. **Review F4: downgrading the buffer migration with withdrawals present broke the next upgrade.** The column was dropped, the row stayed, and the CHECK rejected it on upgrade. Fix (`29a9c7e`, PR B): the downgrade refuses while withdrawals exist. Proved by `test_BF_10_buffer_withdrawals_downgrade_refuses_while_withdrawals_exist` (B61).
4. **The test harness left `payday_runs` rows behind.** Not a product bug.
   - Root cause: the concurrency harness's `_clean_up` deletes every per-user table except the new `payday_runs`. The first PD-03 run left 2 rows; their users are unique, but any row makes the migration downgrade test refuse.
   - Fix: `_clean_up` deletes `PaydayRun`. The 2 rows were removed by hand, and the test DB was checked to hold none.
5. **Test-side issues found while building.** These were fixed in the tests, not by loosening:
   - One `payday_runs` CHECK case broke two CHECKs at once (an unknown outcome with an amount), so the constraint Postgres reported was ambiguous. It now uses amount 0.00, so one CHECK applies.
   - Listing `app.routes` does not show included routers in this FastAPI version, so PD-05 checks with a real request: 401 means the route is mounted, 404 means it is absent.
   - `Result.tuples()` is deprecated in SQLAlchemy 2.1 and is no longer used in the payday tests.
