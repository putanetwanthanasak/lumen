  - All 6 event types are valid: `installment_created`, `cash_withdrawal_created`, `cash_loan_created`, `installment_payment_collected`, `installment_overdue`, `installment_cancelled`.

### Open questions (consolidated, deduplicated; resolved items removed)
1. **WH-05 and JSON numbers:** should webhook money sent as a JSON *number* (not a string) be rejected with 422, the same way `rules.json` rejects it? This is the safest and most consistent reading of the WH-05 decision, but not yet confirmed.
2. **Is the 100 THB per-item cap a hard maximum?** (review M2) CLAUDE.md says "maximum 100 THB per item". 03 lets the user adjust the cap, with only a lower bound. Today nothing (DB, config or engine) stops a cap above 100.
3. **`event_id` uniqueness scope:** (review M1) `webhook_events.event_id` is a global PK. If two vendors could reuse an id, a real event would be dropped as a duplicate. Do we assume event ids are globally unique, or key on (`vendor`, `event_id`)?
4. **INV-6 and late fees:** (review L4) `paid_amount <= principal + fee_total`. A payment that includes accrued late fees on an overdue contract would be rejected unless late fees are rolled into `fee_total` first. Which model do we want?
5. **Tie the auto-save user to the event user?** (review L6) `savings_transactions.user_id` isn't linked to the source event's `user_id`. Should we add a composite FK, or leave it to the service and reconcile?
6. **A DB backstop for INV-5?** INV-5 is now enforced in `compute_saving` and the config, but the DB would still accept an auto-save for a cash-kind installment. Should we add a trigger, or rely on the engine plus tests?
