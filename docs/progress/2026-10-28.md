- **`GET /debts/months[?count=N]`** (`app/debts/months.py`):

The buffer is spent on the remaining gaps in date order. (BS-05, BS-07)
  - The month boundary is checked twice: the query reads `for_month >= this month`, and the plan counts a month only inside an over-budget span. (BS-06)

### Bugs found
1. **A double tap moved the money twice on the real server.**
   - Symptom: two clicks on "ใช้กันชนจ่ายส่วนที่เกิน" in the same task moved it twice. `demo-over`'s buffer went 5,700.00 → 2,700.00, and October showed 3,000.00 prepared.
   - Root cause: the guard was React state (`busy`, `request`). Both clicks ran before the re-render, so each built its own request with a new id.
   - Fix: `mover`, a guard in a closure. A press while a move is out returns null.
   - Proving tests: `UI_47_two_presses_in_the_same_task_send_one_move` (B-UI-183). The real-server walk now shows 5,700.00 → 4,200.00.
   - The mock tests could not catch this: they never clicked twice before a render.
2. **Two month cards could move at once (review round 1 F1).**
   - Symptom: pressing Nov and then Dec before Nov's answer arrived sent both moves. Dec's "before" came from the first load, and if Nov's answer arrived last it put an older balance on screen.
   - Root cause: each card had its own `mover`, so a press was blocked only inside its own card. `refresh()` also never updated the balance it showed.
   - Fix (`0861ba3`):
     - one `MoveLock` for the screen, with the other buttons disabled while a move is out;
     - "before" read from the latest balance when the move starts;
     - `latestOnly`, so an older `GET /buffer` answer is never shown.
   - Proving tests: `UI_47_a_move_for_another_month_waits_while_one_is_out` and `UI_47_an_older_balance_never_replaces_a_newer_one` (B-UI-196 to B-UI-198).
   - On the real server: October and November pressed in the same task moved once (5,700.00 → 4,200.00); November then showed "กันชน 4,200.00 → 2,700.00 บาท", and the summary "เตรียมเงินจากกันชนครบทุกเดือนที่เกินงบแล้ว".
3. **A month's move with an unknown outcome lost its retry (review round 2 F1).**
   - The backend commits the ledger row, then calls the bank. If the bank call fails, only a retry under the same key finishes it (`app/buffer/service.py` `move_to_main`).
   - Root cause: after the error the screen read the shortfalls again. They already counted the month as prepared, so the card dropped its button even though `BUFFER.failed` says "กดย้ายอีกครั้ง".
   - Fix (`25fc0a4`): `Mover.kept()` and `cardMove`. The card offers the kept move, with the same amount, month and id, until it is answered.
   - Proving test: `UI_47_a_move_with_an_unknown_outcome_keeps_its_button_and_its_id` (B-UI-202 to B-UI-205).
4. **Reopening the buffer screen mid-move could send a second id (review round 2 F2).**
   - Root cause: the lock and the kept requests lived in the component, so a remount started fresh.
   - Fix (`25fc0a4`): `moverRegistry` keeps them for the page. A reopened screen waits for the move that is out, then reads again, and "ย้ายอีกจำนวน" waits too.
   - Proving test: `UI_47_a_screen_reopened_while_a_move_is_out_cannot_send_a_second_one` (B-UI-206, B-UI-207).
5. **Blind spot (B-UI-190):** no test checked that the month's button sends its month. Without it the month never turns prepared. Added `UI_47_the_months_button_moves_for_its_month_and_the_free_move_for_none` in `504533a`, then broke again: it fails.

### Deviations from docs/spec and why

- **The bell has no badge**, because the API keeps no read state.
- **`--mode mock` keeps the mock** for dev, the scenes and `nav-layer-check.mjs`.
- **Persona names:** only ม่อน has a name. The others greet with "สวัสดี" alone and show "ผู้ใช้ (id)" in the switcher, so no names were invented.
