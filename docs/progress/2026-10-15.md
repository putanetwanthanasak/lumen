## Session 6: Webhook receiver

### Decisions (decided by the user; 1 to 7 before implementation, 8 after the bug was found)
1. The `installment_overdue` payload carries the platform's **cumulative** `late_fees_accrued`, not an increment.
2. `contract.kind` must match `event_type`. A mismatch is a 422.
3. `overdue_days` is required at creation; there is no silent default.
4. Signatures must be lowercase hex only.
5. **The same `(vendor, event_id)` with a different payload** is checked by comparing a SHA-256 of the canonical JSON (sorted keys, no whitespace).
   - Identical payload: 200 `duplicate`.
   - Different payload: 409 `{"detail": "event_id reused with different payload"}` plus an audit entry (`webhook_event_id_reused`, both hashes), and the original row is kept.
6. **Body limit is 64 KB**, checked before the signature. Over the limit: 413, nothing written.
7. **The work is split into two PRs**, because together they exceed about 400 changed lines without tests:
   - PR #9: money parser and schemas, about 220 lines.
   - PR #10: the receiver, about 290 lines, stacked on #9 and rebased onto `main` after #9 was merged.
8. **U+0000 and the other C0 control characters** are rejected with a 422 in every string field (decided after the bug was found; see Done).

### Break tests (each restored and confirmed with `cmp`; full suite green after)
1. **`compare_digest` → `==`: no test noticed (363 passed). This is a known limit of unit testing, not a gap to close here.** The comparison gives the same answer either way; only the time it takes changes, and a unit test can't measure that difference reliably. What does protect it:
   - There is exactly one comparison point (`verify`, last check), commented with why it must be constant-time.
   - Code review: the Reading guide points at it.
   - The HMAC itself: a timing attack against `==` needs many requests inside the 300-second window, each rejected with the same 401.

   I didn't add a spy test that only proves `compare_digest` was called.
2. Window 300 → 3600: `test_WH_03_timestamp_outside_window_rejected` (old and future) failed, and so did two `test_each_check_rejects` cases.
3. `parse_money` accepts JSON numbers: 11 failed, including both `test_WH_05_money_as_json_number_rejected` cases, the schema-level JSON-number tests, and the config tests. (Also run on PR #9 alone: 6 failed.)
