- **`app/ledger/service.py`:**
  - `lock_contract`: `pg_advisory_xact_lock` on `(vendor, contract_id)`, taken by every new event before dispatch (see Bugs found).
  - `apply_event`:
    - **Payment:** `paid_amount += amount`; above `principal + fee_total + late_fees_accrued` it is rejected (OR-05, INV-6).

  - A payment, overdue or cancel with no installment yet is stored as `pending_parent` → 202. A resend while still pending → 202 again.

  - Every payment, overdue or cancel gets an audit row, `webhook_event_applied` or `webhook_event_rejected`, with `result`, in addition to `webhook_received`.
  - New `Outcome.REJECTED` → **409** `{"detail": "event conflicts with the installment"}`. The event row stays `rejected`.

#### Bugs found
1. **The pending_parent race (prevented before it shipped).**
   - **Cause:** without a per-contract lock, a payment racing its own created event can commit a `pending_parent` row after the created transaction has already looked for pending rows (it can't see uncommitted ones). The payment then waits forever.
   - **Evidence:** break test 11, 14/20 runs lost payments.
   - **Proving test:** `test_OR_01_payments_racing_their_created_event_are_all_applied`.
2. **A bug in the PB-04 generator (test, not code).**
   - Hypothesis shrank a failure: with resends, paid was 99.99; without, 10.00.
   - **Cause:** the generator could insert a resend *before* the original's first delivery, which changed the delivery order. Two payments of 10.00 and 99.99 on a 100.00 principal: whichever comes first is applied, the other is rejected (OR-05). That is correct order dependence.
   - **Fix:** resends are inserted only after the first delivery. 150/150 pass.

#### Deviations from docs/spec and why
- **Resend of a pending event → 202** `pending_parent`, not 200 `duplicate` (04 5.4). It gives the same answer as the first delivery and hasn't been applied yet.
- **Per-contract advisory lock:** not in 04 section 6. Needed for 5f under concurrency (Bugs found 1).
- **Pending replay order:** `occurred_at`, then `event_id`. `received_at` cannot order them: it is the transaction time.
- **The rejection response is 409**, matching D1 / ID-05. 04 5.4 has no row for it.

#### Open questions
1. **Rejected events, resend answer.** A rejected payment or overdue gets 409 the first time and 200 `duplicate` on a resend, following the D1 / ID-05 precedent. Should a resend get the 409 again, so the platform never reads 200 as "accepted"?
2. **Payment on a cancelled installment:** I record it (`paid_amount` grows, status stays `cancelled`), because money the platform says it collected should be visible. Rejecting it is the other option.
3. **Cancel after `paid_off` sets `cancelled`.** Cancel would also overwrite `disputed`. No installment is disputed until Session 9; worth deciding before "Not me" lands.
4. **Cancel delivered before its created event:** the created event still auto-saves (the saving is advisory and stays, rule 6), then the pending cancel is applied. Should a known-cancelled contract skip the saving instead?
5. **A late fee arriving after `paid_off` reopens it to `active`.** A fee drop that would make `paid_amount` exceed the total owed is rejected (409), not clamped.
6. **R2 bounds** chosen: `months` / `installment_no` ≤ 600 (50 years), `overdue_days` ≤ 36,500 (100 years). OK?
7. **Two overdue events with the same `occurred_at`:** the later delivery wins. The platform's timestamps would have to be unique per contract for full order-independence.
