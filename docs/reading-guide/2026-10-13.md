# Reading guide: 2026-10-13 (end of day 1)

Covers the whole backend as it stands: `main` + PR #4 (saving rule engine, with the INV-5 review fix) + PR #5 (one auto-save per installment). Line numbers refer to the branch named next to each file. Target: about 60 minutes.

## How the pieces fit together today

There is no request path yet. Today's code is the **foundation that will decide what's correct** once webhooks arrive.

- `app/config.py` reads settings from env.
- `app/db.py` provides a lazily created engine and a naming convention, so every constraint has a stable name.
- `app/models.py` declares seven tables. **Postgres itself enforces the invariants** it can express: CHECK, UNIQUE, partial UNIQUE, FK, and an append-only trigger. That way a future service bug hits a database error instead of corrupting money.
- The schema exists only through Alembic migrations, which run once per test session against `lumen_test`. Each test runs inside a rolled-back transaction.
- Separately, `app/rules/` is a **pure** rule engine. A validated `rules.json` feeds `compute_saving`, which turns (item, rate, cap, balance, kind) into a Decimal saving with no I/O.
- The future webhook processor (04 section 6) will glue these together: insert the event (idempotency by PK), insert the installment, call `compute_saving`, insert the auto-save (partial UNIQUEs), and write the audit log, all in one transaction.

## What matters in each must-read file

**1. `tests/conftest.py`**
- **L30–39 `test_db_url`:** refuses any database whose name doesn't end in `_test`. This is the only thing stopping `downgrade base` in the migration test from wiping the dev DB.
- **L42–48 `engine`:** runs `alembic upgrade head` once per session (never `create_all`), so the tests check the real migration.
- **L51–59 `db_session`:** an outer transaction plus `join_transaction_mode="create_savepoint"`. A test can hit an IntegrityError, roll back to the savepoint, and keep going, while the outer rollback still wipes everything.

**2. `tests/db/test_constraints.py`**
- **L30–36 `assert_rejected`:** checks `diag.constraint_name`, not just "some IntegrityError". Without it, a test for INV-6 could pass because a NOT NULL fired instead.
- **L47–103:** the INV-2, INV-3 and INV-6 tests and the FK test.
  - INV-3 (L56–65) deliberately uses a *different* installment for the second row, so only the per-event index can fire.
  - INV-6 (L91–103) checks the boundary: `paid == principal + fee` is accepted, and one cent more is rejected.
- **L168–206:** a table with one bad value per CHECK constraint, all run through a single parametrized test.

**3. `tests/db/test_auto_save_per_installment.py`**
- **The whole file (54 lines).** It's the scenario the review found: the same contract resent under `evt-2` must not save twice.

**4. `tests/db/test_audit_log.py`**

## Self-check questions

Answer each one before opening it.

**1. Where does a float get rejected on the config path, and where on the engine path?**
<details><summary>Answer</summary>

- **Config:** `_decimal_from_string` in `app/rules/config.py` rejects anything that isn't a JSON *string*, so `0.05` written as a number fails at load.
- **Engine:** `_require_decimal` raises `ValueError` on `isinstance(value, float)` before anything else.
- **Tests:** they never construct floats, except the one negative test that proves the rejection.
</details>

**2. What does `compute_saving` return for a 201.10 item at 5%, and which test would fail if someone switched to `ROUND_DOWN` or `ROUND_HALF_EVEN`?**
<details><summary>Answer</summary>

10.06 (10.055 rounded half up). `test_rounding_is_half_up_at_half_cent` catches both: `201.10 → 10.06` fails under ROUND_DOWN, and `1000.10 → 50.01` fails under ROUND_HALF_EVEN (50.005 would go to 50.00). Before that test existed, only PB-01 caught ROUND_DOWN, and only probabilistically.
</details>

**3. A balance of exactly 550.00 and a saving of 50.00: does it save? And at 549.99?**
<details><summary>Answer</summary>

At 550.00, yes: 50.00 is saved, because 550 − 50 = 500 and the skip condition is the strict `balance − saving < protected_min` (RE-06). At 549.99 it saves 0.00 (RE-07). It never saves part of the amount, either: RE-08 and the PB-02 `else` branch prove that.
</details>

**4. The same webhook arrives twice with the same `event_id`. What in the database stops a second auto-save, even if the service code is wrong?**
<details><summary>Answer</summary>

Two layers:
1. `webhook_events.event_id` is the primary key (`pk_webhook_events`), so the second event insert fails. The processor's `ON CONFLICT DO NOTHING` will treat that as a duplicate.
2. Even if a service skipped that check, the partial UNIQUE index `uq_savings_transactions_auto_save_source_event_id` (WHERE `type='auto_save'`) rejects a second auto-save for that event. That's INV-3.
</details>

**5. Why does INV-3 also need the CHECK `type <> 'auto_save' OR source_event_id IS NOT NULL`?**
<details><summary>Answer</summary>

In a UNIQUE index, NULLs never collide. Without the CHECK, any number of auto-saves with `source_event_id = NULL` would sit next to each other and slip past INV-3. The CHECK forces every auto-save to carry the event it came from. PR #5 adds the same pairing for `installment_id`.
</details>

**6. The platform resends the same contract under a *new* `event_id`. What blocks a second saving now, and what was missing before the review?**
<details><summary>Answer</summary>

Before PR #5, nothing at the savings layer: INV-3 is per event, and the new event_id is different. Only `uq_installments_vendor_contract_id` blocked the second *installment* row, so a service that saved first or swallowed that error would save twice. PR #5 links each auto-save to its installment and adds the partial UNIQUE `uq_savings_transactions_auto_save_installment_id`. That's ID-05 at the money layer.
</details>

**7. Which invariants from 05 section 3 can't be enforced by the database, and where will they be enforced instead?**
<details><summary>Answer</summary>

- **INV-1** (balance = Σ auto_save − Σ withdrawal) spans tables. It will be checked by `reconcile.assert_user_invariants` before commit.
- **INV-4's upper bound** depends on the `per_item_cap` in force at the time.
- **INV-5** needs the event or installment kind. It's now enforced in `compute_saving` (the kind gate) and in config validation, but not in the DB.
- **INV-7** is about behavior (cancelling doesn't touch savings).

All of these become service-level tests.
</details>

**8. How do you know `audit_log` is really append-only, and why are there two triggers?**
<details><summary>Answer</summary>

`audit_log_append_only` is a BEFORE UPDATE OR DELETE, FOR EACH ROW trigger that raises SQLSTATE 42501. TRUNCATE doesn't fire row triggers, so `audit_log_no_truncate` is a separate statement-level trigger. `test_audit_log.py` asserts the SQLSTATE and the message for UPDATE (Core and ORM), DELETE and TRUNCATE. Break test 2 (trigger removed) failed exactly those 4 tests.
</details>

**9. Why does every constraint test assert the constraint *name*, and what makes those names stable?**
<details><summary>Answer</summary>

A row can violate more than one rule, and Postgres reports whichever fires first: CHECKs in alphabetical order by name, and NOT NULL before those. Asserting only "IntegrityError" would let a test pass for the wrong reason. The names are stable because of `NAMING_CONVENTION` in `app/db.py` (`ck_<table>_<name>`, `uq_<table>_<cols>`, and so on), which the migration also uses.
</details>

**10. `alembic check` passes. Does that prove the migration matches the models?**
<details><summary>Answer</summary>

No. Autogenerate doesn't compare CHECK constraints, and doesn't compare server defaults unless `compare_server_default` is set. It also may not compare partial-index WHERE clauses. PR #5's CHECK had to be added by hand because autogenerate missed it. The constraint tests are what actually prove each rule exists in the migrated DB. A stronger drift test is an open question.
</details>

**11. Why is `compute_saving` keyword-only, and why does it take `kind`?**
<details><summary>Answer</summary>

- **Keyword-only:** every money argument is a `Decimal`, so `compute_saving(500, 10000, ...)` with two arguments swapped would type-check and silently compute nonsense. Keyword-only makes that impossible.
- **`kind`:** without it, INV-5 (cash withdrawals and cash loans never save) depended on every caller remembering to check. The review found `applies_to_kinds` was validated but never used.
</details>

**12. What stops the destructive migration test from wiping your dev database?**
<details><summary>Answer</summary>

`test_db_url` in `tests/conftest.py` fails the run unless the database name in `TEST_DATABASE_URL` ends with `_test`. The migration test runs `downgrade base` only through the session `engine` fixture, which depends on that guard.
</details>
