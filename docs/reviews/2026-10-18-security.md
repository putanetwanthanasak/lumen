## Findings

### S1: medium (known, R4 still open). The bank transfer runs before COMMIT and has no idempotency key

**Why medium:** it is the one path where real money and the ledger can disagree. Today the bank is an in-memory mock and the trigger (a failing COMMIT) is rare, which is why this is medium and not high.

**Evidence**
- `processor.py:183-186`: the transfer runs inside `process_event`, before the caller commits:
  ```python
  # Step 5c, last: money moves only once the ledger rows have passed reconcile.
  if saving > ZERO:
      bank.transfer_to_savings(event.user_ref, saving)
  return Result(outcome, notification_id)
  ```
- `router.py:95`: `session.commit()` only runs afterwards.
- `providers/base.py:7`: `transfer_to_savings(self, user_id: str, amount: Decimal)` has no key, so a provider has nothing to dedupe on.

**Failure scenario**
1. A signed `installment_created` for 800.00 arrives for an opted-in user.
2. Reconcile passes, and the bank is debited 80.00.
3. COMMIT fails (the connection drops, a failover, or the process is killed between the two lines).
4. Result: the debit happened, but there is no `savings_transactions` row and no `webhook_events` row. The platform retries, the event is new again, and the user is debited 80.00 a second time.
5. The same happens with a real bank whose transfer call times out after it actually succeeded: the exception rolls back the ledger, the retry transfers again.

**Suggested fix:** the planned transactional outbox (R4).
- In the webhook transaction, insert a `pending_transfers` row keyed by `savings_transactions.id`.
- After commit, a worker calls `transfer_to_savings(..., idempotency_key=savings_tx_id)` and marks the row done.
- Add the key to the `BankAccountProvider` protocol now, so the real provider can dedupe.

**Proving test:** inject a session whose `commit()` raises after `process_event` returns. Assert that the mock bank balance is unchanged and that no transfer was recorded. A second test: the bank raises *after* applying the transfer, then the event is retried, and the bank must be debited exactly once.

### S2: medium. The app runs as the Postgres superuser and owns every table

**Why medium:** it is defense in depth, not a direct exploit, because no SQL injection was found. But it turns any future injection or credential leak into full database control and an audit-log wipe. R10 recorded this as "info" (table owner only). The live role is worse: it is a superuser.

**Evidence**
- `docker-compose.yml:6-7`: `POSTGRES_USER` is the image's bootstrap superuser.
- Local `.env`: the user in `DATABASE_URL` is the same as `POSTGRES_USER` (checked without printing values).
- Live probe: `rolsuper, rolcreaterole, rolcreatedb, rolbypassrls = true, true, true, true`, and `tableowner = current_user` for all 8 tables, `audit_log` included.
- The audit protection is only a trigger: `alembic/versions/20261013_fbad38bfcc28_initial_schema.py:20-36` (`audit_log_append_only`, `audit_log_no_truncate`).

**Failure scenario:** any code path, or anyone holding `DATABASE_URL`, can do one of these in one session:
- `SET session_replication_role = replica; DELETE FROM audit_log ...`. Superusers skip ordinary triggers in replica mode.
- `ALTER TABLE audit_log DISABLE TRIGGER audit_log_append_only`.
- `TRUNCATE` / `DROP`.
- `COPY ... TO PROGRAM`, which runs OS commands in the DB container.

Dispute history (`installment_disputed` rows) and the webhook audit trail could then be silently erased or rewritten.

**Suggested fix**
- Keep the superuser for `alembic upgrade` only (`MIGRATION_DATABASE_URL`).
- Create a `lumen_app` role: `NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS`, with no ownership.
- Grants:
  - `SELECT, INSERT` on `audit_log` only.
  - `SELECT, INSERT, UPDATE` on `installments`, `webhook_events`, `user_balances`, `user_settings`, `notifications`.
  - `SELECT, INSERT` on `savings_transactions`.
  - No `DELETE` / `TRUNCATE` anywhere.
  - `USAGE` on the schema.
- Put the role creation in `docker/postgres/init/` and point `DATABASE_URL` at it.

**Proving test:** a `db` test that connects with the app URL and asserts four things:
- `NOT rolsuper` for `current_user`.
- `has_table_privilege(current_user, 'audit_log', 'UPDATE')`, `'DELETE'` and `'TRUNCATE'` are all false.
- `SET session_replication_role = replica` raises `InsufficientPrivilege`.
- `ALTER TABLE audit_log DISABLE TRIGGER ...` raises.

### S3: medium (known/accepted). No end-user auth: `X-Demo-User` is trusted as the identity

**Why medium:** this is accepted for the demo (L60 1), and loopback-only binding limits who can reach it. It is the textbook API1/API2 failure if the port is ever exposed, and S8 shows that loopback alone does not fully contain it.

**Evidence**
- `users.py:18-23`: the header value, once it matches `Id`, *is* the user.
- `debts/router.py:15` (`GET /debts/summary`) returns every installment, its UUID, `contract_id`, `item_name` and amounts for that user.
- `disputes/router.py:93-111` (`POST /debts/{id}/not-me`) is scoped by that header only. The owner check (`disputes/service.py:53-57`) is correct, but it trusts the header.

**Failure scenario:**
1. `GET /debts/summary` with `X-Demo-User: <victim user_ref>` returns the victim's debts and installment ids.
2. `POST /debts/<id>/not-me` with the same header disputes the victim's debt, signals the platform, and writes a permanent audit row.

There is no undo (L60 7), and the platform receives a false fraud report. User refs are platform ids that may be guessable.

**Suggested fix:** before any non-loopback use, replace `demo_user` with real auth: a signed session or JWT that binds `user_ref` server-side. Until then, keep loopback-only and add S8's Host check.

**Proving test:** a request without valid credentials, or with a header naming another user, gets 401/404 on both endpoints and writes nothing (the existing `other_user` 404 test, extended to the credential).

### S4: medium (known/accepted). The "Not me" platform signal is fire-and-forget, and the message claims success

**Why medium:** the platform is the only party that can act on a fraud report (L42). Today a failed signal is lost for good, and the user is told it was sent.

**Evidence**
- `disputes/router.py:112-119`:
  ```python
  if result.first_report:
      try:
          platform.signal_dispute(...)
      except Exception:
          logger.exception("dispute signal failed for installment %s", result.installment_id)
  return _response(result)
  ```
- `disputes/router.py:39-42`: `MESSAGE` always says "...และส่งเรื่องให้ {vendor} ตรวจสอบแล้ว".
- L60 (2, 3) requires the signal status (`sent`/`failed`) to be stored and the message to depend on it. Neither is implemented: there is no column and only one message.
- `disputes/service.py:68-84`: `first_report` is true only once, so a repeat tap never re-sends.

**Failure scenario:**
1. The platform API raises or times out on the first tap.
2. The user sees "the report has been sent to ShopDemo".
3. Nothing is stored about the failure, and every later tap returns `first_report=False`, so the signal is never attempted again.
4. The fraudulent debt stays live on the platform while the user believes it was reported.

**Suggested fix:**
- Add `installments.dispute_signal_status` (`pending`/`sent`/`failed`), set to `pending` in the dispute transaction.
- Update it after the call.
- Choose the L60 (3) message from it.
- Re-attempt on a repeat tap while it is not `sent`.
- Later, move it to the R4 outbox.

**Proving test:** run with `MockPlatformProvider` set to raise. Assert that the response carries the L60 "failed" message, the stored status is `failed`, and a second tap calls the provider again and, on success, gives `sent` and the "sent" message.

### S5: low. Concurrent new debts can carry an understated L43 monthly total

**Why low:** the alert itself is always stored and pushed (L58). Only the total it quotes is stale, and only under concurrency for one user. It matters most in the fraud case L58 targets: several cash withdrawals or loans in quick succession.

**Evidence**
- `savings/service.py:40-46`: cash kinds and users without auto-save `return ZERO` *before* `_lock_balance` (`:52`). Only opted-in purchases are serialised per user.
- `notifications/service.py:42`: `monthly_total=summary(session, event.user_ref).monthly_total` reads under READ COMMITTED, so it cannot see another in-flight transaction's installment.
- `lock_contract` (`ledger/service.py:102-111`) is per contract, not per user.

**Failure scenario:**
1. The user has 1,000.00/month of existing debts.
2. Two signed `cash_loan_created` events for different contracts (monthly 2,000.00 each) arrive at the same moment.
3. Both alerts say "ยอดผ่อนรวมต่อเดือนตอนนี้ 3,000 บาท", but the true total after both commit is 5,000.

**Suggested fix:** take a per-user transaction advisory lock (`pg_advisory_xact_lock(hashtextextended('user:'||user_ref,0))`) at the start of step 5 for created events, before `create_installment`. Then `summary()` runs after any concurrent created event for that user has committed.

**Proving test:** a `concurrency` test that sends two created events for one user (cash kinds) in parallel threads, then asserts that the alert committed last quotes the sum of both.

### S6: low (known, R4). The push is inline after commit, with no durable retry

**Why low:** the row is the record and stays in the inbox (`delivery_status='pending'`). The gap is only that the push is never attempted again. This is accepted roadmap R4.

**Evidence**
- `router.py:95-98`: commit, then `notifications.deliver(...)` in the request thread.
- `notifications/service.py:62-86`: up to `push_max_attempts` synchronous tries, with no timeout around `push.send`.

**Failure scenario:**
- The process dies between `commit()` and `deliver()`, and the alert for a new cash loan is never pushed.
- Or a real push provider hangs, which holds the webhook response open until the platform times out. The resend is then answered `duplicate` and is harmless.

**Suggested fix:** the R4 outbox, where a worker picks up `delivery_status='pending'` rows older than N seconds. Put a hard timeout on the provider call.

**Proving test:** commit an event with `deliver` patched to raise `SystemExit`, run the worker once, and assert the row becomes `pushed` with one attempt.

### S7: low. `paid_amount` can overflow `Numeric(12,2)`, a poison event

**Why low:** it needs absurd values (above 10 billion baht) from an authenticated vendor. It is the same class as review R2: a 500 on every retry instead of a 4xx.

**Evidence**
- `money.py` caps each money field at 10 integer digits (`MONEY_PATTERN`). So `owed()` (`ledger/service.py:122-124`), which is principal + fee_total + late_fees_accrued, can reach about 3.0E10.
- `ledger/service.py:136-139` accepts any payment while `paid <= owed(installment)`.
- `paid_amount` is `Numeric(12,2)` (`models.py:40,172`), so its maximum is 9,999,999,999.99.
- Probe: `SELECT cast(19999999999.98 AS numeric(12,2))` gives `NumericValueOutOfRange: numeric field overflow`.

**Failure scenario:**
1. A contract has principal 9,999,999,999.99 and fee_total 9,999,999,999.99.
2. Payment 1 of 9,999,999,999.99 is applied.
3. Payment 2 of 1.00 passes the INV-6 check, and the flush raises `DataError`, which is a 500.
4. The platform retries forever, and every later event for that contract queues behind it.

**Suggested fix:** in `apply_event`, reject (store as rejected, 409) when the new `paid_amount`, or `late_fees_accrued`, would exceed `Decimal("9999999999.99")`. Or validate at contract creation that `principal + fee_total` fits, and cap late fees the same way.

**Proving test:** a WH/OR-style HTTP test using the two payments above, expecting the second to get 409 `rejected` with `paid_amount` unchanged (not 500).

### S8: low. No Host-header validation, so DNS rebinding gets around loopback-only

**Why low:** it needs a targeted attacker page opened on the demo machine while the server runs. But it defeats the only control S3 relies on, and the fix is one line.

**Evidence**
- `main.py:7`: `FastAPI(title="Lumen")` has no `TrustedHostMiddleware`.
- Probe: `GET /health` with `Host: attacker.example:8000` returns 200.
- CORS is not enabled, which is good: cross-origin JS cannot send `X-Demo-User`. But after a DNS rebind the browser treats the page as same-origin.

**Failure scenario:**
1. The demo laptop runs the API on 127.0.0.1:8000, and the presenter opens a link to `http://rebind.attacker.example:8000`.
2. After the DNS TTL, that name resolves to 127.0.0.1.
3. The page's JS calls `GET /debts/summary` with `X-Demo-User: demo_user_1` and reads the ledger, then `POST`s `/debts/{id}/not-me`.

**Suggested fix:** `app.add_middleware(TrustedHostMiddleware, allowed_hosts=["127.0.0.1", "localhost", "testserver"])`.

**Proving test:** `client.get("/health", headers={"Host": "attacker.example"})` returns 400.

### S9: low. The ASGI server is not pinned in the lock file

**Why low:** it is supply-chain and configuration hygiene (hard rule 9). Today it means the documented start command fails, and whatever server someone installs by hand is unpinned and unaudited. pip-audit cannot see it.

**Evidence**
- `pyproject.toml:7-14` has no `uvicorn`, and `uv.lock` has no `uvicorn` entry.
- `README.md:22` says `uv run uvicorn app.main:app --reload`.
- `uv run --frozen python -c "import uvicorn"` gives `ModuleNotFoundError`.

**Failure scenario:**
1. To start the demo, someone runs `pip install uvicorn` or `uv run --with uvicorn ...`, which pulls whatever version is current.
2. Or they copy a snippet with `--host 0.0.0.0`.
3. That exposes S3 to the LAN. No locked, audited version of the server stands between the network and the app.

**Suggested fix:**
- `uv add "uvicorn==<current>"` so it is in `uv.lock` and covered by pip-audit.
- Add an explicit `--host 127.0.0.1` to the README command.
- Drop `--reload` for the demo run.

**Proving test:** a CI step `uv run --frozen python -c "import uvicorn"` and the existing pip-audit job over the export.

### S10: low. Audit rows filed under the event's claimed user

**Why low:** nothing reads the audit by user today. If a per-user activity view is added, it would disclose one user's installment id to another user (API3).

**Evidence**
- `processor.py:117-125` (`webhook_event_id_reused`) and `:214-222` (`webhook_event_rejected`, including `USER_MISMATCH`) write `user_id=event.user_ref` with `ref_id=str(installment.id)`.
- For `USER_MISMATCH`, by definition, that installment belongs to someone else.

**Failure scenario:**
1. A platform bug sends a payment for user A's contract with `user_ref: B`.
2. The audit row has `user_id=B` and `ref_id=<A's installment UUID>`.
3. If audit is ever shown per user, B sees A's installment id, and with S3 B can then dispute it.

**Suggested fix:** for `USER_MISMATCH`, record `user_id=installment.user_id` and put the claimed `user_ref` in `detail`. For id reuse, record the stored row's `user_id`.

**Proving test:** a payment with a mismatched `user_ref` writes an audit row whose `user_id` is the installment owner, and `detail.claimed_user_ref` is the event's.

### S11: low. Resource limits stop at 64 KB per body

**Why low:** the only writer is the authenticated vendor, and the reader is loopback-only.

**Evidence**
- `processor.py:147-150`: any `contract_id` without an installment is stored `pending_parent`, with no count or age limit.
- `debts/service.py:86-91`: `summary()` loads every installment of the user, with no pagination. It runs on every new-debt alert too (`notifications/service.py:42`).
- `router.py:48-55`: the body stream has a size cap but no time cap. Uvicorn's defaults do not bound a slow body.

**Failure scenario:**
- A misbehaving vendor sends 1M payments for nonexistent contracts. Each is a stored row, a 202, an advisory lock and an audit row.
- Or one user gets tens of thousands of installments, and every new-debt alert does a full scan.

**Suggested fix:**
- A per-vendor rate limit at the edge.
- A sweep that marks `pending_parent` rows older than N days as `expired`, with audit.
- `limit`/`cursor` on the summary list, with totals still computed in SQL.
- A server request timeout.

**Proving test:** a summary over more than N installments returns a page plus correct SQL-side totals. A pending row older than N days is expired by the sweep.

### S12: low. Personal data can reach logs, and the API docs are public

**Why low:** logs are local, and the data is pseudonymous user refs and amounts, not names or account numbers.

**Evidence**
- `notifications/service.py:84-86` `logger.exception(...)`, and FastAPI's default 500 logging, print SQLAlchemy exceptions. Those include `[parameters: ...]` (user_id, alert title/body with amounts) because `make_engine` (`db.py:29`) does not set `hide_parameters=True`.
- `reconcile.py:29` and `savings/service.py:114-116` put `user_id` in exception messages that are logged.
- `/docs`, `/redoc` and `/openapi.json` are served (probe: 200). That is fine for a demo, but it is an unauthenticated map of the API (API9).

**Failure scenario:** a DB error during `deliver` writes `user_id` and the full Thai alert text with amounts into the server log. Logs are often shipped or shared while debugging.

**Suggested fix:**
- `create_engine(..., hide_parameters=True)`.
- Log user refs hashed, or not at all, in error paths.
- `FastAPI(docs_url=None, redoc_url=None, openapi_url=None)` unless `DEBUG`.

**Proving test:** force an `IntegrityError` in `deliver`, capture logs with `caplog`, and assert that neither the user_ref nor the body text appears.

## Checked and found OK

**Secrets**
- Settings come from env only (`config.py:10-29`). Secrets are `SecretStr`, and every default is `None`.
- A missing or empty webhook secret fails closed, with every webhook 401 (`signature.py:52-53`).
- `.env` is ignored (`.gitignore:2`), and only `.env.example` (blank values) is tracked.
- A history grep of all 73 commits found no assigned secret values.
- CI has a full-history secret-scan job (`.github/workflows/ci.yml:86`), and CI Postgres credentials are throwaway.
- Nothing prints settings, and no `print()` exists in `app/`.

**HMAC (`webhooks/signature.py`, `webhooks/router.py`)**
- The signed message is `timestamp + "." + raw body bytes`, verified before parsing, so the verified bytes are the parsed bytes (`signature.py:34-36`, `router.py:63-72` then `:86`).
- `hmac.compare_digest` is used (`signature.py:63`).
- ±300 s window (`:58`). The timestamp is ASCII digits only and limited to 12 characters (`:18`). The signature is lowercase hex only, 64 characters (L55, `:19`).
- The vendor is bound by per-vendor secret lookup (`:52`), so a body signed with one vendor's secret cannot be presented as another vendor's.
- Order: 64 KB streamed cap (413, before auth, L55, `router.py:48-55`), then signature (401, one fixed body for every failure, `:73-75`), then schema (422), then one transaction.
- A replay inside the window is answered by `(vendor, event_id)` idempotency.

**Parsing**
- Strict pydantic, `extra="forbid"` at every level (`schemas.py:327`). Money is strings only (`money.py:237`, `fullmatch`, ASCII `[0-9]`). C0 controls are rejected (`schemas.py:314`).
- Probe: a lone surrogate `\ud800` is rejected by `parse_event` (422), so it never reaches psycopg as a 500.
- Probe: duplicate keys resolve last-wins in both `parse_event` and `json.loads`, so the validated event and the stored payload agree.

**Idempotency and races**
- `INSERT ... ON CONFLICT (vendor, event_id) DO NOTHING RETURNING` (`processor.py:86-99`).
- A different payload gives 409 plus audit, with the original row untouched (`:116-126`).
- The resend of a rejected event gets the same 409 (`:113-114`, L59 1).
- Contract uniqueness (`ledger/service.py:77`).
- A per-contract advisory xact lock serialises created / payment / overdue / cancel / dispute (`ledger/service.py:102-111`, `disputes/service.py:63`).
- One alert per installment via a partial unique index (`notifications/service.py:45-59`, migration `ba626805b6a1`). Only the inserting transaction gets the id, so a resend never re-pushes.
- One dispute audit row per installment (migration `55f5b32ae8fb:41-47`).

**Ledger rules**
- A user mismatch on payment / overdue / cancel is rejected, never applied (`ledger/service.py:132-133`). It covers replayed `pending_parent` events too (`processor.py:232-235` goes through `_apply`).
- Overdue sets the cumulative fee, never adds it (`:147`). A stale older overdue changes nothing (`:167-184`). A fee drop below paid is rejected (`:144-145`, L59 5).
- A cancel never touches savings or `disputed_at` (`:149-151`), and `_settle` never changes `disputed`/`cancelled` (`:157-164`).
- Reconcile runs before the transfer, and a violation rolls back everything (`processor.py:171-181`).

**Alerts**
- The copy uses only trusted config and formatted numbers, with no webhook free text such as `item_name` (`notifications/copy.py:59-76`), so the push cannot carry injected text.
- `deliver` never raises into the webhook response (`notifications/service.py:84-86`, RS-03).

**"Not me"**
- The owner check is in the query (`disputes/service.py:53-57`).
- A malformed UUID, an unknown id and another user's id all return the same 404 (`disputes/router.py:104-110`), so there is no existence oracle beyond S3.
- The dispute is idempotent under concurrency: the conditional `UPDATE ... WHERE disputed_at IS NULL RETURNING` (`disputes/service.py:68-84`).
- The signal is sent once, after commit (`disputes/router.py:111-112`).
- Contacts are clearly marked mock (`.example` domain, all-zero phone).

**Errors**
- 401 / 404 / 409 / 413 / 422 bodies are fixed strings. The 422 body has `type` and `loc` only (L60 4).
- Unhandled errors return Starlette's plain `Internal Server Error`, with no debug mode, stack trace or SQL in the response.

**SQL**
- Only the ORM / Core is used. The one `text()` is a constant (`NEW_DEBT_KIND_SQL`). No string-built SQL was found (hard rule 8).
- The Postgres port is bound to `127.0.0.1` (`docker-compose.yml:10-12`).

**Migrations**
- `ba626805b6a1` and `55f5b32ae8fb` add only constraints, an index and a nullable column. No data rewrite, and no grant or privilege change.
- Both are checked by the schema snapshot test (it passes in the 626-test run).
